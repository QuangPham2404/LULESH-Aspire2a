# 2026-07-29 Progress

## Session Summary

This session set up the initial structure and operating model for using Codex as
an HPC workflow assistant for LULESH optimization on Aspire2A.

The intended workflow is:

1. User and Codex discuss optimization ideas, with the user leading technical
   direction.
2. Codex writes or modifies scripts for builds, PBS runs, extraction, and
   analysis.
3. User reviews non-routine scripts before job submission.
4. Codex submits PBS jobs, records metadata, captures failures, and patches
   build/run issues when appropriate.
5. Codex extracts and analyzes results first, then the user reviews the
   findings and decides the next optimization step.
6. For simple sweeps such as compiler flags, compilers, or MPI libraries, Codex
   can carry out the full loop after the experiment scope is clear.

## Current State

The repository now has a flexible structure intended to be reusable across
optimization projects without over-planning application-specific details:

```text
builds/
experiments/
planning/
progress/
results/
scripts/
AGENTS.md
README.md
.gitignore
```

Directory decisions:

- `builds/` contains build-related material only.
- `builds/source/` is for source trees cloned or copied for building.
- `builds/build-scripts/` is for reusable build scripts kept for record and
  handoff.
- `builds/extra-packages/` is for approved extra packages/libraries needed to
  support builds.
- `experiments/` contains one subdirectory per optimization run or run family,
  for example `ICC25-O3/` or `ICC25-O2/`.
- Each experiment directory should hold its run script, a concise `README.md`
  with purpose and metadata, and raw PBS output files such as `.o` and `.e`.
- `planning/` replaces the earlier `analysis/` idea. Planning and result
  analysis are kept together, mainly in `planning/PLANS.md`, so the project
  story is not split across multiple locations.
- `progress/` contains date-based technical diary files such as this one.
- `results/` contains extracted results from raw experiment output.
- `results/scripts/` contains result-specific extraction, parsing, cleaning, or
  plotting scripts.
- top-level `scripts/` is only for general workflow helpers such as repository
  checks, remote state checks, or Git-aware workflow utilities.

Git/sync decision:

- The earlier idea of Aspire2A being only an untracked copy was replaced.
- Going forward, both the local PC and Aspire2A should use real Git clones of
  this repository.
- Local Git operations are still preferred for commits and pushes.
- Aspire2A should not store GitHub credentials.
- Codex should not push from Aspire2A without explicit user approval.
- Aspire2A remains the remote build/run environment.

Ignore policy:

- `.gitignore` was added with a minimal policy.
- Ignored by default:
  - `builds/source/*`
  - `builds/extra-packages/*`
  - generated build directories such as `build/` and `cmake-build-*/`
  - compiled artifacts such as `*.o`, `*.obj`, `*.a`, `*.so`, `*.dylib`,
    `*.dll`, `*.exe`, and `*.mod`
- `builds/source/README.md`, optional future `builds/source/SOURCES.md`, and
  `builds/extra-packages/README.md` remain trackable.
- Raw PBS output files like `job.o12345` and `job.e12345` remain visible to Git
  unless future policy changes. The reasoning is that small raw text logs can be
  useful as handoff data for teammates.
